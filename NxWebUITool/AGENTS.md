# AGENTS.md

## 1. 最高优先级

**正确性 > 验证 > 可维护性 > Token 节省。**

Token 优化只能减少重复、无关和低价值上下文，不得减少完成任务所必需的代码阅读、分析、API 确认和验证。

当证据不足、调用关系不明确、API/版本不确定或局部代码不足以判断正确性时，必须主动扩大上下文，禁止猜测。

未完成合理验证时，不得声称任务已完全完成。

---

## 2. 默认工作流程

**任务 → PROJECT_STATE → 搜索定位 → 局部读取 → 判断影响范围 → 修改 → 验证 → 必要时继续修复 → 简洁汇报**

仅当架构、关键接口、重要技术决策或项目状态发生明显变化时更新 `PROJECT_STATE.md`。

---

## 3. 文件读取

默认：

**搜索符号 → 定位代码 → 局部读取 → 必要时扩大范围**

禁止为了“了解项目”而无目的扫描整个仓库。

### HARD RULE

**Do not re-read unchanged files unless the current task requires details no longer available in context.**

除非当前任务确实需要上下文中已经不可用的细节，否则禁止重新读取未修改文件。

以下情况允许或要求重新读取/扩大范围：

* 文件刚被修改，需要确认最终状态
* 上下文已缺失关键细节
* 新错误与该文件有关
* 之前仅查看局部，现在需要完整上下文
* 调用关系、生命周期或数据流不明确
* 怀疑之前的理解有误
* 修改公共 API、核心数据结构或跨模块接口
* 涉及线程、构建系统、序列化、几何拓扑等跨模块影响

硬性规则不得阻止正确性所必需的读取。

---

## 4. 搜索与工具调用

优先搜索：

**精确符号 / 类 / 函数 / 类型 → 调用点 → 错误信息 → 文件名 → 关键词**

结果过多时先限制目录、模块或文件类型。

禁止：

* 重复执行没有新信息的相同搜索
* 无目的遍历整个仓库
* 为了确认已经明确的事实反复调用工具
* 将大量无关第三方源码或日志送入上下文

每次工具调用都应提供新的必要信息或完成实际操作。

---

## 5. 修改原则

采用**最小必要修改**。

不要：

* 顺手重构无关模块
* 无理由改接口、数据布局或命名
* 仅为了代码风格重写稳定代码
* 为减少 Token 跳过必要逻辑

如果局部修复会产生明显错误架构、重复逻辑或长期技术债务，可以扩大修改范围，但必须有明确技术理由。

---

## 6. 验证原则

执行**最小充分验证**，而不是最小验证。

优先从低成本验证开始：

**静态检查 → 相关模块/Target 编译 → 相关测试 → 集成测试 → 必要时全量构建/测试**

以下修改应提高验证级别：

* 公共 API / 基础库
* 核心数据结构
* 核心几何算法
* 多线程 / 生命周期 / 内存管理
* 序列化 / 文件格式
* 构建系统
* 跨模块接口
* 大范围重构

不得为了减少 Token 或工具调用而跳过必要验证。

---

## 7. Debug

默认：

**复现 → 收集证据 → 定位 → 提出假设 → 验证假设 → 修改 → 再验证**

避免：

**猜测 → 修改 → 再猜测 → 继续叠加补丁**

修复失败后应重新检查证据和假设。

日志默认只保留：

* error / fatal
* exception / assert
* stack trace
* 相关 warning
* 错误附近必要上下文

如果完整初始化过程影响问题判断，可以扩大日志范围。

---

## 8. C++ 规则

修改 C++ 时根据任务检查：

* 生命周期与所有权
* RAII
* nullptr / 悬空引用
* 越界与 iterator 失效
* 未初始化数据
* copy / move
* const 正确性
* ABI / API 兼容
* 异常安全
* 线程安全 / 数据竞争
* 第三方库版本差异

**编译通过不等于逻辑正确。**

---

## 9. CAD / 几何 / 数值算法

涉及以下领域时，不得为了节省 Token 过度压缩分析：

* NURBS / B-Spline / Bezier
* Patch / Sweep / Loft / Trim / Boolean
* BRep / Tessellation
* 曲线闭环 / 曲面拟合
* G0/G1/G2/G3+
* 法线 / UV / 曲率
* STEP / IGES / 3DM
* 几何容差
* 数值求解

始终遵循：

**几何正确性与数值稳定性 > Token 节省。**

根据问题检查：

* 参数域与单位
* UV / 曲线 / 曲面方向
* 法线与 orientation
* degree / knot / control points / weights
* tolerance
* 边界条件
* degeneracy
* topology
* numerical conditioning

遇到 NaN、Inf、不收敛、奇异矩阵、曲面振荡、法线翻转、UV 异常、曲率异常或几何裂缝时，应先检查输入、容差、参数域、方向、索引、边界条件、退化情况和数值条件，再判断是否需要替换算法。

不要未经证据直接重写整个算法。

---

## 10. 性能优化

性能修改必须尽量基于证据。

流程：

**测量 → 定位 hotspot → 修改 → 再测量**

确认瓶颈属于 CPU、GPU、内存、IO、锁竞争、数据复制、重复计算、算法复杂度、渲染或第三方 API 后再优化。

禁止仅凭感觉进行大规模性能重构。

---

## 11. 模块隔离

UI、业务逻辑、几何内核和 IO 默认独立定位。

UI 问题不要默认读取整个几何内核；几何问题不要默认读取完整 UI。

但事件、线程、生命周期、数据绑定或调用链跨层时，必须读取相关层。

第三方 API 已确认时不要读取大量第三方源码；版本/API/ABI 不确定或实际行为异常时必须确认，禁止凭记忆猜测版本相关接口。

---

## 12. PROJECT_STATE.md

用于保存会影响后续开发的重要信息：

* 当前目标
* 已完成的重要功能
* 核心架构
* 关键文件与 API
* 已确认技术决策
* 已验证结论
* 已知问题
* 下一步任务

不要记录：

* 完整聊天历史
* 每次微小修改
* 大量临时日志
* 已失效或无关的过程信息

保持简洁，只保存后续 Agent 真正需要知道的状态。

---

## 13. Token 优化边界

优先减少：

* 重复读取
* 重复搜索
* 无关源码
* 无用日志
* 重复需求
* 重复解释
* 无关第三方内容
* 过长最终回复

不得减少：

* 必要代码上下文
* 调用关系
* API/版本确认
* 错误证据
* 必要测试
* 数值分析
* 几何验证
* 安全性检查

发生冲突时，始终优先正确完成任务。

---

## 14. 完成与回复

只有在代码已实际修改并完成合理验证后才能声明“完成”。

无法执行某项验证时必须明确说明：

**代码修改已完成，但仍有部分内容未进行运行时验证。**

最终回复默认只包含：

### 已完成

* 关键修改

### 验证

* 实际执行的编译 / 测试及结果

### 注意

* 未验证内容、剩余风险或阻塞问题

不存在的部分可以省略。

不要重复粘贴完整需求、大段源码或完整日志。

---

## 核心原则

**少读无关内容，不少读必要内容。**

**不重复读取，但允许为正确性重新取证。**

**少做重复工作，不少做验证。**

**减少 Token，不降低工程正确性。**
